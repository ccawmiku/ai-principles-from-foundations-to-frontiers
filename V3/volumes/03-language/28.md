在算法论文中，一个包含 700 亿甚至上万亿参数的大模型往往只是一串优雅的数学公式。
但对于一线系统架构师和基础设施工程师而言，这是一场惊心动魄的硬件物理突围战：

- 一台普通的单卡 GPU（即使是顶配 80GB 显存），面对 70B 模型时，连最基础的模型权重都塞不下；
- 面对 405B 的超级巨无霸，哪怕把 8 张卡捆在一台服务器里，也会瞬间爆显存死锁；
- 在数千张 GPU 组成的分布式大机房里，如何把一个巨大的模型平整地切成碎片、分发给不同芯片，并在微秒级的时钟节奏下完成海量数据的跨机协同？

这一章我们就戴上安全帽，走进大模型工程的重型装备车间。我们不讲抽象的理论口号，而是算清每一块显存的去向，讲透现代大规模分布式训练与推理的底层系统架构。

<a id="section-01"></a>
## 1. 显存的四重大山：权重、梯度、优化器状态与中间激活

许多新手工程师在采购算力时，往往只拿“参数量 $\times 2$ 字节”去估算显存，结果一跑代码就秒遭 `CUDA Out of Memory`。
在大模型训练期间，显存里到底挤着哪四座大山？

```
┌────────────────────────────────────────────────────────┐
│ 1. 静态模型权重 (FP16/BF16): 2 字节 / 参数               │
├────────────────────────────────────────────────────────┤
│ 2. 反向传播梯度 (FP16/BF16): 2 字节 / 参数               │
├────────────────────────────────────────────────────────┤
│ 3. AdamW 优化器状态 (FP32 主权重 + 一阶动量 + 二阶方差):   │
│    4 + 4 + 4 = 12 字节 / 参数 (极其沉重的大山！)         │
├────────────────────────────────────────────────────────┤
│ 4. 前向中间激活值 (Activations) + KV Cache:            │
│    随 Batch Size 与序列长度呈爆发式动态膨胀             │
└────────────────────────────────────────────────────────┘
```

单单前三项（权重 + 梯度 + 优化器状态），每个参数就需要吞噬：
$$2 + 2 + 12 = \mathbf{16\text{ 字节显存}}$$
这意味着：**训练一个 70B 参数的模型，哪怕 Batch Size 设为 1，光这三项静态硬开销就需要吃掉整整 $70 \times 16 = 1120\text{ GB}$ 显存！** 必须至少动用 14 张 80GB 的 H100 显卡才能勉强装下！

再加上第 4 项——为了反向传播求导而必须缓存在内存里的中间激活值（Activations），显存开销会进一步暴涨。为此，业界广泛采用**激活重计算（Activation Checkpointing）**：前向传播时不保留所有中间激活，反向传播用到时现场重新跑一遍前向算子，以区区 30% 的额外计算时间，直接省下 70% 的激活显存！

<a id="section-02"></a>
## 2. KV Cache 真实显存精算：手算 400 步上下文的 9.83 MB（9,830,400 字节）

在推理服务阶段，虽然没有了梯度和优化器状态，但我们在第 24 章见过的 **KV Cache** 依然会随着对话长度的延伸而吞噬海量显存。

让我们拿起算盘，为一个教学级小型语言模型的单次推理请求手算一次真实的 KV Cache 显存占用：
- 网络深度：$L = 24$ 层 Transformer
- 当前上下文长度：$n = 400$ 个 Token
- 键值头数：$h_{\text{kv}} = 4$ 个 KV 头（采用 GQA 优化）
- 每个头的特征维度：$d_{\text{head}} = 64$
- 浮点精度：FP16 存储（每个数值占 2 字节）
- 缓存对象：Key 矩阵与 Value 矩阵各存一份（乘系数 2）

我们将这些物理维度连乘起来：
$$\text{KV Cache 字节数} = 24 (\text{层}) \times 400 (\text{词}) \times 4 (\text{头}) \times 64 (\text{维}) \times 2 (\text{K与V}) \times 2 (\text{字节})$$

一步步相乘核算：
$$24 \times 400 = 9,600$$
$$9,600 \times 4 = 38,400$$
$$38,400 \times 64 = 2,457,600$$
$$2,457,600 \times 2 = 4,915,200$$
$$4,915,200 \times 2 = \mathbf{9,830,400\text{ 字节}}$$

精准算得 **$9,830,400$ 字节**（约为 **$9.38\text{ MiB}$**）！

观察这个算式的残酷放大效应：
- 如果这还不是 GQA，而是标准的 16 头 MHA，缓存立刻膨胀 4 倍到 37.5 MiB；
- 如果上下文长度从 400 步拉长到 40,000 步，单个用户的缓存直接飙升到近 1 GB！
- 如果线上同时有 500 个用户并发提问，服务器光存缓存就需要吃掉 500 GB 显存！

正是这种分毫必争的物理现实，倒逼全行业必须在硬件通信与内存布局上进行极限压榨。

<a id="section-03"></a>
## 3. FlashAttention 的 IO 革命：为什么无需在显存中落地 n 方大矩阵

在标准注意力计算中，最让 GPU 头疼的是：
计算 $Q K^\top$ 会产生一个 $n \times n$ 的巨大中间方阵。当序列长度 $n = 32,000$ 时，这个方阵包含 10 亿个浮点数！
传统的 PyTorch 实现会傻乎乎地**把这 10 亿个浮点数完整写出到外部慢速大显存（HBM）中，然后再把它读回片上缓存去算 Softmax，算完再写出到 HBM，然后再读回乘上 $V$**。
显卡的核心芯片（SRAM）算力极强，但大部分时间都在无聊地等待数据在芯片与外存之间搬运（IO 堵塞）。

2022 年 Tri Dao 提出的 **FlashAttention** 彻底引爆了一场显存 IO 革命：
它的哲学极其硬核：**绝不允许在显存里完整落地那个 $n \times n$ 的大方阵！**
- 利用 **Tiling（分块分片）** 技术：把大矩阵切分成刚好能塞进 GPU 片上超高速一级缓存（SRAM）的小方块；
- 利用 **在线 Softmax（Online Softmax）** 技巧：一边分块计算点积，一边动态维护局部最大值与归一化累积系数；
- 算完一块小注意力的结果就直接加到输出上，用完立即在片上丢弃！

FlashAttention 的计算结果在数学上与标准自注意力**完全严格等价**，但彻底消灭了 $n \times n$ 大矩阵对外存的疯狂读写，**直接将长文本注意力速度拉快了 2~4 倍，显存开销从原本的 $O(n^2)$ 暴降为严格线性的 $O(n)$**！

<a id="section-04"></a>
## 4. 分布式 3D 并行宇宙：数据并行（DP）、张量并行（TP）与流水线并行（PP）

面对单张显卡无论如何也塞不下的千亿超大模型，微软、英伟达等工业巨头联合构筑了经典的 **3D 并行体系（Megatron-DeepSpeed）**：

```
                              [3D 并行空间]
                                    ▲
                                   /│\
                                  / │ \
                                 /  │  \
     [数据并行 (DP)] ───────────┼───┼───┼─────────── [张量并行 (TP)]
     不同机器跑不同样本          │  │  │            把单层大矩阵横纵切开
     最后 All-Reduce 同步梯度    │  │  │            依赖卡间超高速 NVLink
                                \   │   /
                                 \  │  /
                                  \ │ /
                                   \│/
                                    ▼
                             [流水线并行 (PP)]
                             按网络层数横向切分
                             第 1~8 层在卡 1，第 9~16 层在卡 2
```

1. **张量并行（Tensor Parallelism, TP）**：
   **在“单层内部动手术”**。把一个超大矩阵乘法（如 16384 维的投影）切成 8 份，由单台服务器里的 8 张 GPU 各算一个切片，再通过极速的片间物理互联通道（NVLink，带宽高达 900 GB/s）飞速同步合并。
2. **流水线并行（Pipeline Parallelism, PP）**：
   **在“网络深度上动手术”**。把 80 层的大模型像切香肠一样切开：卡 1 负责第 1~20 层，算完把特征送给卡 2 算第 21~40 层。
   - **痛点：流水线气泡（Bubble）**——卡 2 在等卡 1 算完之前，只能傻坐着干等。工程师设计了 1F1B（一前向一反向）精巧微批次穿插调度，将空闲气泡压缩到极低比例。
3. **数据并行（Data Parallelism, DP）**：
   **在“批次样本上动手术”**。每台机器上跑一份完整的模型切片副本，各吃各的数据批次，算完各自的局部梯度后，通过全局 All-Reduce 同步全网梯度。

<a id="section-05"></a>
## 5. 零冗余优化器（ZeRO）：Stage 1、2、3 怎样粉碎单卡显存墙

传统的纯数据并行极其浪费：每张卡上都要完完整整存一份 16 字节/参数的参数、梯度与优化器状态。
微软 DeepSpeed 团队提出的 **ZeRO（Zero Redundancy Optimizer）** 彻底打破了这种冗余：

| ZeRO 阶段 | 核心动作 | 单卡显存优化效果 | 通信代价 |
| :--- | :--- | :--- | :--- |
| **ZeRO-Stage 1** | **把优化器状态切碎**（分片到各卡上，每张卡只维护自己那份参数的动量与方差） | 显存直接暴降 **4 倍**！单卡仅需 4 字节优化器状态 | **完全不增加**额外通信量 |
| **ZeRO-Stage 2** | **进一步把梯度也切碎**（每张卡只计算和保存自己那份参数的局部梯度） | 显存开销再次砍半！ | **完全不增加**额外通信量 |
| **ZeRO-Stage 3** | **终极合体：连模型参数本身也切碎！** 每张卡只保留 $1/N$ 的模型权重；前向时动态广播拉取，算完立刻销毁释放 | **彻底粉碎单卡显存限制**！显存与卡数严格成反比，千亿模型可塞入普通集群 | 带来约 50% 的额外跨卡前向通信开销 |

在今天的大模型研发中，**ZeRO-Stage 3（以及 PyTorch 原生支持的 FSDP, Fully Sharded Data Parallel）** 已经成为训练大模型的基础事实标准。

<a id="section-06"></a>
## 6. 算力与通信的拔河：为什么千卡集群不能做简单乘法

在算力规划时，最容易犯的一个幼稚错误是：
“单张 H100 算力是 1000 TFLOPs，我买 10,000 张卡，总算力就是 $1000 \times 10,000 = 10,000,000\text{ TFLOPs}$！”

**真实的物理世界从来不是线性乘法！随着集群卡数从 8 卡扩大到 1 万卡，通信开销会呈指数级狂飙！**
- **机内通信**：8 张卡插在同一张主板上，有 900 GB/s 的奢华 NVLink 互联，极速飞驰；
- **跨机通信**：一旦走出机箱，数据只能通过普通的机房网线或 InfiniBand 交换机传输，带宽瞬间缩水十倍以上！
- **木桶短板效应**：在 1 万张卡的超大规模同步中，只要有一张卡因为过热发生降频、或者一根光纤发生毫秒级的微小网络抖动，其余 9999 张卡就必须全部在原地挂起等待（All-Reduce 同步挂起）！

这就是为什么各大头部实验室不惜斥资数亿美元打造超大规模 RoCE/InfiniBand 低延迟无损网络，并通过精密的通信-计算重叠掩盖技术，把模型算力利用率（MFU）拼死守在 40%~55% 的黄金区间。

<a id="section-07"></a>
## 7. 现代推理架构的胜利：PagedAttention 与连续批处理（Continuous Batching）

在推理服务领域，工程界同样诞生了堪称艺术的系统级突破：

### 1. PagedAttention（借鉴操作系统的虚拟内存分页）
传统的推理引擎在用户请求进来时，必须在显存中预先切出一块足够容纳最长 2048 词的**连续物理显存空间**：
- 如果用户实际只聊了 50 个字就退出了，剩下 97% 的预留空间全被白白占着，产生海量的内部内存碎片！
- **PagedAttention（vLLM）** 借鉴了操作系统的页表思想：把 KV Cache 打散成一个个微小的固定大小内存页（比如每页存 16 个 Token）。显存物理上可以完全支离破碎，逻辑上通过页表串成虚拟连续空间。显存浪费从 80% 骤降至不到 4%！

### 2. 连续批处理（Continuous Batching）
传统的批处理是“木桶打水”：4 个人一组，必须等那个问了三千字长篇大论的用户彻底答完，其余 3 个问了一句话早就回答完的用户才能结单、整台服务器才能接下一批。
**连续批处理（Iteration-level Scheduling）** 实现了极速动态调度：在每一个 Token 生成的时钟间隙，答完的请求瞬间离场释放资源，排队的新请求瞬间插队进入，GPU 的矩阵乘法吞吐量原地拉满！

然而，在现实业务场景中，用户常常希望模型处理极其庞大的信息：一次性阅读整套 10 万字的《红楼梦》、分析几百页的上市公司财务年报。
